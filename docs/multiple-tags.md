# Multiple tags in a single build

One build can publish the same image under several tags. Layers, the config
blob, and the manifest are built once; with `--push`, blobs are uploaded once
and the manifest is pushed once per tag.

## CLI

```bash
pycontainer build --push \
  --tag ghcr.io/me/app:v1.2.3 \
  --tag ghcr.io/me/app:stable
```

`--tag` is repeatable. The first value is the primary tag (used for the build
result and as the default push target) and must be a full reference. Later
values may be full references in the same repository or bare tags, for example
`--tag ghcr.io/me/app:v1 --tag v2`.

### Semantic version expansion

```bash
pycontainer build --tag ghcr.io/me/app:v1.2.3 --semver-tags --latest
```

| Flag | Effect |
|------|--------|
| `--semver-tags` | `v1.2.3` also gets `v1.2` and `v1` (a `v` prefix is optional) |
| `--latest` | also adds `latest` (opt-in, never implicit) |

Pre-release versions such as `v1.2.3-rc1` are not expanded. Using
`--semver-tags` when no tag looks like `MAJOR.MINOR.PATCH` is an error.

### Git-derived versions

```bash
pycontainer build --context . --tag ghcr.io/me/app \
  --tag-from-git --semver-tags --latest
```

`--tag-from-git` replaces the version of the first image reference with the
result of `git describe --tags --exact-match` for the context's HEAD. Other
explicit tags remain in the same repository and participate in expansion as
usual. If multiple Git tags point at HEAD, Git selects the exact match.
Branches and tags on ancestor commits do not count.

Git and an existing worktree with a HEAD commit are required. If HEAD has no
exact tag, `--git-fallback sha` opts into `sha-` followed by the first 12
characters of the commit ID; otherwise the build fails. Git tags that are not
valid OCI tags are rejected rather than rewritten. A SHA fallback is not a
semantic version, so `--semver-tags` requires another stable version tag.

Tracked changes, staged changes and untracked files anywhere in the Git
worktree cause an error unless `--allow-dirty` is explicitly supplied. As with
Git status, ignored files are not considered dirty; ensure they cannot affect
the image if it must correspond to the commit. Git is inspected again when
the build starts; a changed HEAD or selected tag requires a new configuration.
Before publishing the local layout, HEAD and the selected Git tag are checked
again, and the worktree must still be clean unless `--allow-dirty` was supplied.
Untracked files generated by this build in the output and cache locations and
the builder's output lock file are excluded from this final cleanliness check;
tracked changes there are still detected. The checks do not freeze source files,
so do not modify the worktree during a build. Before each registry tag is
published, an exact Git tag must still point at the built commit;
checking out another commit after a successful build does not change the image
being pushed. No Git tag is created or moved.

With `--registry`, omit the destination's tag or use the same Git-derived
version; a conflicting tag or digest is rejected.

## Configuration file

```toml
[build]
tag = "ghcr.io/me/app:v1.2.3"
tags = ["stable", "ghcr.io/me/app:prod"]
semver-tags = true
latest-tag = true
```

On the command line, any `--tag` replaces both `tag` and `tags` from the file.

Git-derived tagging can also be enabled in the file:

```toml
[build]
tag = "ghcr.io/me/app"
tag_from_git = true
git_fallback = "sha" # optional
```

Dirty worktrees require the command-line `--allow-dirty` opt-in; it cannot be
enabled in the configuration file.

## Validation

- Tags must match the OCI tag syntax (`[A-Za-z0-9_][A-Za-z0-9_.-]{0,127}`).
- Every full reference must target the same registry and repository as the
  primary tag; otherwise the build fails with a message naming both.
- Digest references are rejected.
- Duplicates are removed.

## Output

The OCI layout gets one `refs/tags/<tag>` file per tag, all pointing at the
same manifest or index digest. After a push, `builder.pushed_refs` lists every
pushed reference. For multi-platform index pushes, it is reset at the start of each
attempt and records confirmed successes as they happen. If a tag push fails,
the error reports confirmed pushes, the failed or unknown-outcome reference,
and references not attempted, regardless of progress output; tags are not
rolled back. A single `--tag` behaves exactly as before.

For multi-platform builds, the layout `index.json` has one image-index
descriptor per configured tag. Each has the same digest and size, and an
`org.opencontainers.image.ref.name` annotation holding the full configured
reference (for example `registry.example/team/app:stable`). Because several
descriptors exist, select with an explicit reference such as
`oci:<layout>:registry.example/team/app:stable`. Hermetic tests check this
descriptor shape; a Skopeo selection test runs only when Skopeo is installed.
